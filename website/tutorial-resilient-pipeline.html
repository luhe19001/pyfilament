Get started · ~10 min

Build a resilient pipeline with pyfilament.

Fetch and process a batch of web pages — through flaky networks, repeated work, and impatient servers — and watch every run live in a dashboard.

What you'll build

A small page-fetching pipeline: fetch → process → pipeline, hardened one keyword at a time, then scaled out across worker processes.

What you'll learn

  • Retries & timeouts for flaky work
  • Caching to skip repeated work
  • Rate & concurrency limits
  • Subtasks and worker queues
  • The live dashboard
1

Get set up

pyfilament leans on Redis (caching, queues, limits) and a database (SQLite by default). Cloning the repo is the fastest start — it ships the dashboard UI and the migrations too.

terminalcopy
# 1. clone the project (needs Python 3.14+)
git clone https://github.com/pyfilament/pyfilament
cd pyfilament

# 2. create & activate a virtualenv — use this SAME env for every step
python3.14 -m venv .venv
source .venv/bin/activate

# 3. install pyfilament + the SQLite driver
pip install -e . aiosqlite

# 4. start Redis  (Docker Desktop must be running first; no Docker?
#    brew install redis && brew services start redis)
docker run -d -p 6379:6379 redis

# 5. create the database tables (writes ./filament.sqlite)
alembic upgrade head

Run every step from this terminal — activated .venv, inside pyfilament/ — so everything points at the same database.

Two errors beginners hit here, both from drifting out of that setup:

  • No module named 'filament.db' — wrong environment; re-run source .venv/bin/activate.
  • no such table: task_type — wrong folder; stay in pyfilament/, or set the DB path (note the four slashes): export FILAMENT_DB_URI="sqlite+aiosqlite:////path/to/pyfilament/filament.sqlite"

Already have a project? pip install pyfilament drops the library into any app — just bring your own Redis and a migrated database.

2

Your first task

Add @task to any async function. Calling it returns a run; awaiting the run executes it. That's the whole API.

app.pycopy
import asyncio
from filament import task

@task
async def hello(name):
    return f"hello, {name}"

print(asyncio.run(hello("filament")))
▸python app.py  →  hello, filament

Nothing fancy yet — but that run is already in the database. It turns up in Step 8.

3

Survive a flaky network

Real fetches fail and hang. tries adds automatic retries (exponential backoff + jitter); timeout aborts a run that overruns. get_logger() writes per-run logs that stream to the dashboard (Step 8), not your console.

app.pycopy
import asyncio
from filament import task, get_logger

attempts = 0

@task(tries=4, delay=0.5, timeout=10)
async def fetch(url):
    global attempts
    attempts += 1
    get_logger().info(f"GET {url} (attempt {attempts})")
    await asyncio.sleep(0.2)               # network latency
    if attempts < 3:                       # fail twice, then recover
        raise ConnectionError("temporary failure")
    return f"<html>{url}</html>"

print(asyncio.run(fetch("https://example.com")))
▸fails twice, retries, recovers on attempt 3  →  <html>https://example.com</html>

The failures are scripted so the demo always lands; real code just raises real exceptions. Narrow what retries with retry_exceptions=[...] / no_retry_exceptions=[...].

4

Don't fetch the same thing twice

cache=True stores the result. The next call with the same arguments skips the body entirely and returns the stored value — until cache_ttl expires.

app.pycopy
calls = 0

@task(tries=4, delay=0.5, timeout=10, cache=True, cache_ttl=3600)
async def fetch(url):
    global calls
    calls += 1                              # count real executions of the body
    await asyncio.sleep(0.2)
    return f"<html>{url}</html>"

async def main():
    a = await fetch("https://example.com", refresh_cache=True)  # force one fresh run
    b = await fetch("https://example.com")                      # served from cache
    print("same result:", a == b, "| body ran", calls, "time(s)")

asyncio.run(main())
▸same result: True | body ran 1 time(s)

The cache lives in Redis and survives restarts — hence refresh_cache=True on the first call, to force one fresh run for the demo.

5

Be a good citizen

Hammer a server and you'll get blocked. rate_limit caps executions per second; max_concurrent caps how many run at once — both enforced across every worker, not just one process.

app.pycopy
@task(
    tries=4, delay=0.5, timeout=10,
    cache=True, cache_ttl=3600,
    rate_limit=5,            # at most 5 fetches / second, fleet-wide
    max_concurrent=10,       # at most 10 in flight at once
)
async def fetch(url):
    ...

No matter how many callers — or workers (Step 7) — pile on, fetch stays within these limits.

6

Compose a pipeline from subtasks

Tasks can call other tasks. Each call is its own tracked run, so you get a clean parent → child tree. Here a pipeline walks the URLs and each process fetches a page, then counts its words — reusing fetch from above.

app.pycopy
@task
async def word_count(html):
    return len(html.split())

@task
async def process(url):
    page = await fetch(url)              # subtask 1
    words = await word_count(page)       # subtask 2
    return {"url": url, "words": words}

@task
async def pipeline(urls):
    results = []
    for url in urls:                     # one at a time = a clean tree
        results.append(await process(url))
    return results

print(asyncio.run(pipeline(["https://a.com", "https://b.com"])))
▸[{'url': 'https://a.com', 'words': 1}, {'url': 'https://b.com', 'words': 1}]

Want them in parallel? Skip asyncio.gather — hand the URLs to workers instead. That's what the next step's queue is for.

7

Scale out with workers

Move fetch off the caller and onto a queue. .request(...) enqueues a job to Redis and hands back a run; a separate worker pulls jobs with .serve(). Put the shared definitions in tasks.py (no asyncio.run at the bottom) so the worker and producer can import them — three files, one folder.

tasks.py  — shared definitionscopy
import asyncio
from filament import task, get_logger

@task(tries=4, delay=0.5, timeout=10)
async def fetch(url):
    get_logger().info(f"GET {url}")
    await asyncio.sleep(0.2)
    return f"<html>{url}</html>"
worker.py  — terminal 1copy
import anyio
from tasks import fetch

anyio.run(fetch.serve)        # pull fetch jobs off the queue, forever
producer.py  — terminal 2copy
import anyio
from tasks import fetch

async def main():
    run = await fetch.request("https://example.com")   # enqueue
    print("worker returned:", await run)               # await the result

anyio.run(main)
▸terminal 2 prints  worker returned: <html>https://example.com</html>  (terminal 1 keeps serving)

Run both commands from the folder holding the three files, or Python can't import tasks. Start as many workers (or machines) as you like — the queue, rate limits and concurrency caps coordinate them all. Pass an anyio.Event to serve() to stop one cleanly.

8

Watch it live in the dashboard

Everything you ran was recorded. Start the API and the UI to browse task types, every run, the state timeline, the subtask tree and streaming logs.

terminalcopy
# API — serves data on port 5006
uvicorn filament.api.main:app --port 5006

# UI — in another terminal, opens on http://localhost:3001
cd ui && npm install && npm run dev

Open localhost:3001 (the UI proxies /api and /graphql to the API on :5006, so keep both running). Every pipeline → process → fetch tree is there — states moving created → running → success, with the get_logger() logs to replay.

address already in use on :5006? You probably already started the API in another tab — just reuse it. Otherwise find and stop the stray process: lsof -i :5006, then kill -9 <PID>.

That's the whole loop: write an async function, add reliability as keywords, scale it across workers, watch every run. No plumbing to maintain.
